1. What is a vector database?

A vector database stores vectors and efficiently finds vectors that are similar to a query vector. In RAG, a vector normally represents a document chunk.

Text chunk
→
Embedding model
384 / 768 / 1536…
→
Vector DB
vector + metadata
Important: the embedding model converts text into vectors. The vector database mainly stores, indexes, filters, and searches those vectors.

Vector

[0.12, -0.44, 0.71, ...]. A fixed-dimensional numerical representation.

Metadata

Examples: document_id, page, tenant_id, user_id, language, timestamp, permissions.

Payload

The chunk text itself or a pointer to where the text is stored.

3. Similarity and distance

Cosine similarity

cos(A,B) = A·B / (||A|| ||B||)

Measures angle. Common for semantic embeddings. Higher is more similar.

Dot product

score = A · B

Fast. If vectors are normalized, its ranking is equivalent to cosine similarity.

Euclidean / L2

d(A,B) = sqrt(Σ(Ai-Bi)²)

Straight-line distance. Lower is closer.

4. Main vector indexes

HNSW — graph-based search

Vectors
→
Graph layers
→
Traverse nearby nodes
→
Nearest vectors

HNSW connects nearby vectors in a navigable graph. Search starts at coarse/high layers and moves toward detailed layers.

ProsCons
Excellent latency/recall trade-off; no training phase; strong general-purpose default.Memory hungry; index construction/update cost; parameters need tuning.

Important knobs: M, efConstruction, and search-time efSearch. More search effort generally improves recall but costs latency.

IVF — inverted file

All vectors
→
Clusters / centroids
→
Search selected lists

Vectors are assigned to coarse regions. A query searches only some regions rather than the entire dataset.

ProsCons
Reduces search work; useful with compression; scalable.Requires training/centroids; recall depends on probe count; more tuning.

Product Quantization — PQ

PQ compresses vectors into compact codes. It saves memory and can speed distance calculations, but introduces approximation error.

ProsCons
Large memory savings; useful for very large collections.Information loss can reduce recall; configuration is more complex.

Flat / brute force

Compare the query with every vector. It is often too slow for huge datasets, but is extremely useful as a ground-truth baseline when evaluating ANN recall.

5. Popular choices

Qdrant

Vector-first database with strong payload filtering and HNSW-based retrieval.

Good for: production RAG/search.

Trade-off: another service to operate.

Milvus

Purpose-built vector database designed for large-scale vector workloads and multiple index/storage options.

Good for: large collections and specialized vector infrastructure.

Trade-off: operational complexity.

Weaviate

Feature-rich vector search platform with semantic/hybrid search and metadata capabilities.

Good for: full-featured semantic search.

Trade-off: larger platform surface.

Chroma

Developer-friendly vector store commonly used for prototypes and smaller applications.

Good for: local development and simple RAG.

Trade-off: validate production scaling needs.

FAISS

A similarity-search library, not a complete database.

Good for: local indexes, experiments, custom retrieval.

Trade-off: you build persistence, metadata, API, tenancy and operations around it.

pgvector

Vector similarity search inside PostgreSQL.

Good for: applications already using Postgres.

Trade-off: a dedicated vector system may be preferable for some very large/specialized workloads.

7. Metadata filtering

Real RAG usually needs vector similarity + filters.

query:
  "What is the refund policy?"

filter:
  tenant_id = "company_A"
  document_type = "policy"
  language = "en"
  user_allowed = true

then:
  similarity search over allowed candidates
  → top K
Security matters: tenant/user authorization should be enforced as part of retrieval constraints, not as an afterthought after results are returned.

8. Storage and scaling

For raw FP32 vectors:

raw bytes ≈ number_of_vectors × dimensions × 4

Example: 1,000,000 chunks × 384 dimensions:

1,000,000 × 384 × 4
= 1,536,000,000 bytes
≈ 1.54 GB

Actual storage is larger because of indexes, metadata, IDs, segments/WAL, replicas and database overhead.

10. Which should you choose?

I already use PostgreSQL

Start by evaluating pgvector. One database can hold relational data, metadata and vectors.

I want a dedicated production vector service

Qdrant is a strong candidate, especially when payload filtering is important.

I have a very large vector workload

Benchmark Qdrant, Milvus, Weaviate and managed services using your real data, filters, latency target and query distribution.

I am experimenting locally

FAISS or Chroma are convenient. FAISS gives lower-level control; Chroma gives a more database-like developer experience.

I need keyword + semantic search

Use hybrid retrieval: combine lexical/BM25-style retrieval with vector retrieval, then optionally rerank.

12. Common misconceptions

❌ Vector DB creates embeddings

Usually your application calls the embedding model; the DB stores/searches the resulting vectors.

❌ Similarity = correctness

A high similarity score is a retrieval signal, not proof that the chunk contains the answer.

❌ Top-10 is always best

K depends on chunking, corpus, reranking and the LLM context budget.

❌ ANN is always necessary

For small collections, exact search can be simple and perfectly adequate.
